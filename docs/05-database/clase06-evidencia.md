## Tablas núcleo incluidas en V1 y por qué

| Tabla | Motivo de selección |
|---|---|
| `unidad` | Entidad raíz del condominio; no depende de otras tablas. |
| `persona` | Actor principal (residentes, personal); no depende de otras tablas. |
| `area_comun` | Recurso que se reserva; no depende de otras tablas. |
| `residencia` | Primera relación 1:N real: vincula persona con unidad (RN-01). |
| `reserva` | Segunda relación: persona y área común, con regla de fechas (RN-02). |

Tablas que se dejaron para después: `visita`, `incidencia` y `tarea_mantenimiento`, porque dependen de procesos (estados y transiciones) que se implementarán con sus módulos.

## Orden de creación

1. `unidad` (sin FK)
2. `persona` (sin FK)
3. `area_comun` (sin FK)
4. `residencia` → `persona`, `unidad`
5. `reserva` → `area_comun`, `persona`

## PK y FK

| Tabla | PK | FK |
|---|---|---|
| `unidad` | `pk_unidad (unidad_id)` | — |
| `persona` | `pk_persona (persona_id)` | — |
| `area_comun` | `pk_area_comun (area_comun_id)` | — |
| `residencia` | `pk_residencia (residencia_id)` | `fk_residencia_persona → persona`, `fk_residencia_unidad → unidad` |
| `reserva` | `pk_reserva (reserva_id)` | `fk_reserva_area_comun → area_comun`, `fk_reserva_persona → persona` |

Todas las PK son `BIGINT GENERATED BY DEFAULT AS IDENTITY`.

## UNIQUE y CHECK

| Constraint | Regla de negocio |
|---|---|
| `uq_unidad_numero (numero_unidad)` | No existen dos unidades con el mismo número. |
| `uq_persona_correo (correo_electronico)` | El correo identifica a una sola persona. |
| `uq_area_comun_nombre (nombre)` | No hay dos áreas comunes con el mismo nombre. |
| `ck_area_comun_capacidad (capacidad > 0)` | El aforo debe ser positivo. |
| `ck_reserva_fechas (fecha_fin > fecha_inicio)` | Una reserva no puede terminar antes de empezar. |

## Dataset mínimo válido

Una fila por tabla núcleo:

```sql
INSERT INTO unidad (numero_unidad, tipo, estado) VALUES ('A-101', 'Departamento', 'ACTIVA');
INSERT INTO persona (nombre, apellido, correo_electronico) VALUES ('Ana', 'Suarez', 'ana@condoflow.com');
INSERT INTO area_comun (nombre, descripcion, capacidad, estado) VALUES ('Piscina', 'Area recreativa', 20, 'ACTIVA');
INSERT INTO residencia (persona_id, unidad_id) VALUES (1, 1);
INSERT INTO reserva (area_comun_id, persona_id, fecha_inicio, fecha_fin, estado)
VALUES (1, 1, '2026-09-02 18:00-04', '2026-09-02 20:00-04', 'CONFIRMADA');
```

## Errores de integridad provocados

Ejecutados después de aplicar V1 sobre una base vacía.

| # | Prueba | Mensaje de PostgreSQL | Explicación |
|---|---|---|---|
| 1 | NOT NULL: persona sin correo | `null value in column "correo_electronico" of relation "persona" violates not-null constraint` | Una persona no puede existir sin correo. |
| 2 | UNIQUE: correo repetido | `duplicate key value violates unique constraint "uq_persona_correo"` | El negocio prohíbe dos personas con el mismo correo. |
| 3 | FOREIGN KEY: residencia con `persona_id = 999` | `insert or update on table "residencia" violates foreign key constraint "fk_residencia_persona"` | No se puede vincular una persona que no existe. |
| 4 | CHECK: área común con capacidad 0 | `new row for relation "area_comun" violates check constraint "ck_area_comun_capacidad"` | La capacidad debe ser mayor que cero. |
| 5 | CHECK: reserva con `fecha_fin` anterior a `fecha_inicio` | `new row for relation "reserva" violates check constraint "ck_reserva_fechas"` | La reserva debe terminar después de empezar. |
